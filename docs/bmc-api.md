# API вебморды Supermicro для Virtual Media

Снято с живой машины 11.08.2026: `X11DPL-i`, BMC FW `1.76`. Публично не
документировано — получено перехватом XHR на странице
**Virtual Media → CD-ROM Image**.

Всё делается через `POST https://<BMC>/cgi/op.cgi`, тело —
`application/x-www-form-urlencoded`, авторизация — cookie `SID`, выдаваемая
`login.cgi`.

Во всех запросах присутствуют два поля, к делу не относящиеся:
`time_stamp` (строка даты в формате JS `Date`) и пустое `_`. Это защита от
кеширования, сгенерированная скриптом морды; на поведение не влияют, но
отправлять их стоит — так запрос неотличим от браузерного.

## Операции

| Действие | Тело | Ответ |
|---|---|---|
| Сохранить настройки образа | `op=config_iso&host=<хост>&path=<путь>&user=<логин>&pwd=<пароль>` | `ok` |
| Смонтировать | `op=mount_iso` | `VMCOMCODE=001` |
| Размонтировать | `op=umount_iso` | — |
| Статус слотов | `op=vm_uiso_status` | XML, см. ниже |

Порядок обязателен: `config_iso` сохраняет параметры в конфигурацию BMC,
`mount_iso` монтирует уже сохранённое. Отдельных параметров у `mount_iso` нет.

Существует также `op=vm_status` — морда дёргает его при открытии страницы.

## Статус

```xml
<?xml version="1.0" ?>
<VM>
  <CODE NO="1"/>
  <DEVICE ID="0" STATUS="4"/>
  <DEVICE ID="1" STATUS="255"/>
  <DEVICE ID="2" STATUS="255"/>
</VM>
```

- `STATUS="4"` — образ смонтирован.
- `STATUS="255"` — слот пуст (`No disk emulation set` в морде).

Это источник правды о состоянии монтирования: опрашивать надо BMC, а не свою
базу (см. `DECISIONS.md`).

## Формат параметров

Проверено на живой машине:

- `host` — адрес SMB-сервера **без схемы и без имени шары**: `185.102.74.23`.
  Схему `http://` прошивка принимает в поле, но при монтировании не отправляет
  ни одного пакета — HTTP-режим неработоспособен, несмотря на подсказку на
  странице.
- `path` — **обратные слэши, начиная с имени шары**: `\iso\test.iso`.
- `user`, `pwd` — учётная запись SMB. **Спецсимволы в пароле прошивка не
  принимает**, только буквы и цифры.
- Максимальный размер образа — **4.7 ГБ**, заявлено самой страницей.

## Воспроизведение без браузера

```sh
BMC=<адрес BMC>
SHARE_HOST=<адрес хоста с шарой>
JAR=$(mktemp)

# 1. Логин. Возвращает cookie SID.
curl -sk -c "$JAR" -d "name=ADMIN&pwd=<пароль BMC>" "https://$BMC/cgi/login.cgi"

# 2. Сохранить параметры образа.
curl -sk -b "$JAR" "https://$BMC/cgi/op.cgi" \
  --data-urlencode "op=config_iso" \
  --data-urlencode "host=$SHARE_HOST" \
  --data-urlencode 'path=\iso\test.iso' \
  --data-urlencode "user=ikvm" \
  --data-urlencode "pwd=<пароль шары>"

# 3. Смонтировать.
curl -sk -b "$JAR" "https://$BMC/cgi/op.cgi" --data-urlencode "op=mount_iso"

# 4. Проверить статус.
curl -sk -b "$JAR" "https://$BMC/cgi/op.cgi" --data-urlencode "op=vm_uiso_status"

# 5. Размонтировать.
curl -sk -b "$JAR" "https://$BMC/cgi/op.cgi" --data-urlencode "op=umount_iso"
```

`-k` обязателен, пока на BMC стоит просроченный самоподписанный сертификат.
После его замены (шаг 2 в `docs/spike.md`) проверку можно включить.

## Не проверено

- Формат полей `login.cgi`: перехват сделан на уже открытой сессии, поэтому имена
  `name`/`pwd` взяты по общепринятой для этой линейки схеме. Часть прошивок
  ожидает значения в base64. Проверяется первым же запуском сценария выше.
- Поведение при попытке смонтировать образ больше 4.7 ГБ.
- Что возвращает `mount_iso` при неуспехе — видели только `VMCOMCODE=001`.
