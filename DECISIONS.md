# Документ решений: ipmi-web

Зафиксировано по итогам разбора 11.08.2026. Это не план на будущее, а описание
принятых решений — если что-то меняется, правим здесь, а не в голове.

**Состояние: этап 0 (спайк) не пройден. Кода нет и до прохождения спайка не будет.**

## Задача

Монтирование ISO на серверы через BMC без Java, без stunnel и без плясок на
машине администратора. Вся грязная работа — на сервере, администратору — браузер.

Отправная точка: на старых Supermicro в консоль можно попасть двумя путями.
HTML5-консоль работает, но не умеет пробрасывать ISO. Java-виджет (`iKVM.jar`)
умеет, но регулярно ломается — версия JRE, политики, сертификаты. Последний
случай: подкладываемый Supermicro `stunnel` отказал по `certificate has expired`
на самоподписанном сертификате самого BMC (`CN=IPMI, O=Super Micro Computer`).

## Ключевое решение

Java-путь (`iKVM.jar`, `SMCIPMITool`) отбрасывается целиком.

Вместо него — **Virtual Media → CD-ROM Image**: сервис держит библиотеку
образов и раздаёт её, **BMC сам забирает** оттуда ISO средствами своей
прошивки. Раздача — по HTTP (изначально предполагался SMB, см. «Пересмотр
11.08.2026»).

Решающий довод: такое монтирование **переживает перезагрузки сервера и рестарт
контейнера**, потому что образ прописан в конфигурации BMC. Установка ОС — это
2–3 перезагрузки, и push-сессия (`SMCIPMITool vmwa`), живущая только пока жив
процесс, разваливается ровно на середине. Дополнительно: `SMCIPMITool` —
проприетарный бинарь, который нельзя законно положить в публичный образ.

Redfish на целевой машине **закрыт лицензией** — `/redfish/v1/` отвечает
`OemLicenseNotPassed`, требует `SUM DCMS OOB`. Покупка лицензии остаётся
запасным выходом для машин, до которых иначе не дотянуться.

## Архитектура

Два компонента, потому что веб-морда, хранящая пароли от всех BMC, не должна
иметь `NET_ADMIN` на хосте.

**`ipmi-web`** — контейнер: Flask 3.0.3 + gunicorn + Flask-SQLAlchemy + SQLite +
APScheduler + cryptography, порт **5006**. Раздача образов идёт по HTTP через
внешний nginx (см. «Пересмотр 11.08.2026») — порт в адресе прошивка не
принимает, поэтому раздача обязана жить на 80/443.

**`ipmi-fw-helper.service`** — хостовый демон, unix-сокет, ровно две операции:
добавить IP в nftables-set на N минут и удалить IP. Компрометация веб-морды
даёт максимум «открыть 445 для произвольного адреса», а не контроль над
файрволом хоста.

Живёт на `itsg-vpn`, за nginx, доступ по VPN либо по списку IP. Деплой как во
всём парке: Dockerfile + GitHub Actions → ghcr.io → `docker compose pull`.
Документацию пушим с `[skip ci]`.

## Топология: pull, а не push

И Redfish `InsertMedia`, и SMB CD-ROM Image — pull-модель. Не сервис толкает
образ в сервер, а **BMC идёт за образом сам**. Требование, соответственно, не
«сервис видит BMC», а **«каждый BMC видит сервис»** — обратно тому, как обычно
строят админки.

Инстанс один, центральный.

## Сетевая модель и принятый риск

Целевой BMC находится на публичном адресе. **Рекомендация была другой** —
убрать BMC из интернета (за VPN или роутер площадки) и поставить сервис внутри
той же сети. Принято решение оставить BMC снаружи и открывать доступ точечно.

Изначально это означало SMB1/NTLMv1, доступный из интернета, — что и было
принятым риском №2. После перехода на HTTP-раздачу (см. «Пересмотр 11.08.2026»)
наружу смотрит read-only отдача файла, и риск сводится к обычному веб-серверу.

Компенсирующие меры, они же часть задачи:

- **Единственный источник правды о доступе — множество `ikvm.allow` в
  nftables.** Дублировать список в `hosts allow` в `smb.conf` осознанно не
  стали: адреса пришлось бы держать в двух местах, а главное — на каждое
  монтирование сервису пришлось бы переписывать конфиг и перечитывать `smbd`,
  что способно оборвать уже идущую установку.
- Как следствие, набор правил обязан быть **постоянным** (`/etc/nftables.d/`,
  см. `nftables/ikvm.nft`) и с дефолтным `drop`: правила nftables не переживают
  перезагрузку сами, а контейнер поднимается с `restart: unless-stopped` — без
  этого после ребута возможен момент, когда Samba работает, а правил нет.
  Множество при загрузке пустое, то есть состояние по умолчанию — «закрыто».
- Доступ открывается через **named set в nftables с таймаутом**. Ядро
  удаляет элемент само: если сервис упадёт или контейнер убьют, порт всё равно
  закроется.
- **Короткий TTL с автопродлением**, пока BMC подтверждает, что образ
  смонтирован. Фиксированный длинный TTL не годится: истечение посреди
  установки ОС уронит её с невнятной ошибкой ввода-вывода.
- При размонтировании — удаление элемента из set плюс `conntrack -D`, иначе уже
  установленная сессия переживёт закрытие правила.
- Шара только на чтение. Писать туда BMC незачем.

## Функциональность этапа 1

- Инвентарь серверов. **Пароли BMC в базе, шифруются Fernet** — как в
  `srv-control`.
- **Своя авторизация**, не SSO: логин плюс argon2/bcrypt, первый администратор
  создаётся из переменных окружения при первом старте, rate-limit на вход,
  CSRF-токены. **Дефолтных `admin/admin123` нет** — сервис хранит пароли от
  всех BMC, это худшее место в парке для дефолтных учёток.
- Именной аудит-журнал: кто, когда, какой сервер, какой образ, какое действие с
  питанием. Именные пользователи — условие осмысленности журнала, поэтому
  общий пароль и basic-auth на nginx отвергнуты.
- Библиотека ISO: загрузка через браузер (чанковая, резюмируемая) и скачивание
  по URL фоновой задачей. Файлы, положенные через scp, появляются в списке сами
  — библиотека это просто каталог. SHA256 и размер считаются один раз при
  появлении файла.
- Монтирование и размонтирование, **одноразовый** boot override (`cdrom`, без
  `persistent` — постоянный флаг даёт бесконечный цикл установки), питание
  (on / off / reset / graceful shutdown), ссылка на HTML5-консоль BMC.
- **Статус монтирования опрашивается у BMC**, база хранит только историю и
  намерение. Иначе неизбежно расхождение: кто-то отмонтирует через вебморду
  BMC, а мы показываем «смонтировано» и держим порт открытым.

## Форма драйвера

Интерфейс драйвера проектируется **в терминах Redfish** — `insert_media`,
`eject_media`, `set_boot_override`, `power_action` — при одной реализации
(Supermicro). Причина: если ядро примет форму Supermicro-костыля, Redfish потом
будет прикручен сбоку и код останется кривым навсегда. При такой форме
добавление вендора — новый файл, а не переделка ядра.

Сервис должен уметь честно сказать «этот сервер вне доверенного периметра,
SMB-монтирование недоступно» вместо попытки и падения.

## Явно не делаем

- Сенсоры, SEL-журналы, инвентарь железа, состояние дисков — это Zabbix.
- Проксирование KVM-консоли. HTML5-консоль работает, её достаточно, из карточки
  сервера на неё ведёт обычная ссылка.
- `SMCIPMITool` и Java в любом виде.
- Драйвер Redfish — до появления реальной потребности.
- Загрузка ISO по HTTP для Redfish-вендоров — там же.

## Пересмотр 11.08.2026: HTTP вместо SMB

Целевая машина оказалась **`X11DPL-i`, BMC FW 1.76** — платформа X11, а не
X9/X10, из которых исходило исходное рассуждение. Осмотр вебморды дал два
факта, меняющих конструкцию.

**Первое: CD-ROM Image на месте**, поля и кнопки Save / Mount / Umount
присутствуют. Драйвер реализуем, лицензия не нужна — **покупать её решено не
будут**, вопрос закрыт.

**Второе, главное: прошивка принимает HTTP и HTTPS**, а не только
Windows-шару — в требованиях страницы прямо указано
`Input http://Domain, https://Domain, or just Domain`. Поэтому **Samba из
проекта исключается**, образ отдаётся по HTTP. Отпадают: Samba в контейнере,
`server min protocol = NT1`, `ntlm auth = ntlmv1-permitted`, одноразовые
SMB-учётки, открытый наружу порт 445, требование host-network. **Принятый риск
№2 этим снимается** — вместо SMB1/NTLMv1 наружу смотрит read-only отдача файла.

Хостовый `ipmi-fw-helper` с nftables **сохраняется**: окно доступа по времени и
по адресу полезно само по себе, просто теперь оно защищает раздачу файла, а не
протокол класса EternalBlue. Одноразовый SMB-пользователь заменяется
**одноразовым токеном в URL**.

SMB остаётся задокументированным запасным путём на случай, если HTTP-режим на
конкретной прошивке окажется нерабочим.

### Ограничения прошивки, влияющие на реализацию

- **Максимальный размер образа — 4.7 ГБ**, заявлено самой страницей. Windows
  Server 2019 (~5 ГБ) и 2016 (~6.5 ГБ) в лимит не проходят. Сервис обязан
  **проверять размер при добавлении образа и явно отказывать**, а не давать
  смонтировать и получать невнятный отказ в середине установки. Обход для
  Windows — `dism /export-image` с выбрасыванием лишних редакций из
  `install.wim`.
- **Порт в адресе указать нельзя.** Разрешённые символы Share host: `a-z`,
  `A-Z`, `0-9`, `-`, `.`; двоеточия среди них нет. Раздача обязана слушать
  80 или 443, то есть жить за тем же nginx, что и остальной парк.
- Слотов эмуляции три (Device 1–3).
- Формат `Path to image` для HTTP-режима не документирован (в SMB-режиме —
  `\share\file.iso`). Определяется на спайке.

## Непроверенные допущения и принятые риски

1. **Главный риск проекта.** Воспроизводимость Mount/Unmount программно не
   доказана. У кнопки в вебморде BMC нет публично документированного API:
   либо эмуляция логина и POST в `/cgi/op.cgi` (формат плавает между
   прошивками), либо OEM raw-команды IPMI (опкоды Supermicro не опубликованы).
   Снимается на этапе 0. Если не поддастся — возвращаемся к выбору драйвера.
2. ~~SMB1/NTLMv1 доступен из интернета.~~ **Снят** переходом на HTTP-раздачу,
   см. «Пересмотр 11.08.2026». Остаётся общее: BMC на публичном адресе, со
   всеми последствиями из `bmc-hardening.md`.
3. **Риск принят осознанно.** Загрузка сервера с примонтированного образа
   заранее не проверяется — целевая машина боевая и не перезагружается,
   проверка будет по факту проведения работ. Спайк доказывает цепочку по
   данным (образ читается из живой ОС), но не выбор загрузочного устройства
   в BIOS.
4. Не подтверждено фактами: достаёт ли BMC до хоста сервиса (`lan print` не
   снимали), версия прошивки BMC, свободное место под библиотеку образов.
5. Redfish на целевой машине заперт лицензией `SUM DCMS OOB`.
